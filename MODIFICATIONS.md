# Modifications

This file tracks fork-specific changes ported onto `release/v2.2.5` (upstream tag `v2.2.5`, `9bbb8ce18c`) so they are easy to audit, carry forward, or revert when syncing with upstream. The fork design mirrors `release/v1.18.5` (opf18): the **plan agent authors plan files itself** (no system pre-seed). v2.2.5 architectural adaptations are noted inline (the old `packages/opencode` monolith is gone — everything ported into `packages/core` with the new plugin/tool/command domains; Effect plugin API instead of the promise-hooks plugin API). Beyond the ported feature set the fork carries one upstream bugfix (plugin host entrypoint probes, below) plus fork operations notes at the bottom.

Upstream v2.2.5 ships its own conversational `opencode.plan` plugin (plan agent discusses a plan in chat, plan files optional in `~/.opencode/plan`, no tools). This fork **replaces** that plugin's behavior wholesale with the fork design below, keeping the same plugin id.

## ConfigFork (separate `opencode-fork.jsonc`)

- `packages/core/src/config/fork.ts` so fork-only settings live in `opencode-fork.jsonc` / `opencode-fork.json` (vanilla opencode never reads them). Pure Effect loaders — no service/LayerNode: `loadGlobal()` (global files only) and `loadForLocation(location)` (global + project `.opencode/` walk-up, closest project wins). `jsonc-parser` for parsing, deep-merge for stacking.
- `PlanSchema` = `{ path?, name?, prompt? }` (configurable plan dir, filename template, plan-mode reminder prompt). `SearchSchema` = `{ hidden?, ignore? }`. `AgentSchema` = record of `ConfigAgent.Info` for fork-only agent overrides.
- v1.18.5's per-instance `ConfigFork.Service`/`layer`/`node` wiring is gone: consumers call the loaders directly (plugins are location-scoped; `ctx.location` is fixed per plugin instance).
- Post-port fix (`bf31d7e71e`): `loadGlobal` honors `OPENCODE_CONFIG_DIR` like the Global service does (was hardcoded to the default config root), and a missing/unreadable fork file resolves empty *inside* the promise — an `Effect.promise` rejection is a defect, so the `.then(undefined, () => undefined)` swallow must happen at the source. Same commit makes `plan-path.ts`'s containment check use the `OPENCODE_CONFIG_DIR`-aware config root.

## Agent-Driven Plan Mode (agent authors plans; no pre-seed)

- `packages/core/src/plugin/plan.ts` reworked from upstream's conversational plan mode to the fork design. Keeps upstream's reminder-reconciliation structure (`ctx.session.hook("context")` splice + `ctx.session.synthetic(..., resume: false)` persistence, `session.created`/`session.agent.selected` switch reminders, `execute.after` BlockedError rewrite) but the enter reminder is **dynamic** — `${planInfo}` reflects the active plan and is recomputed each turn; a stale copy is replaced, not just a missing one.
- `packages/core/src/session/plan.ts` (`SessionPlan`): pure naming helpers + `plan` effect (ported from v1.18.5 `Session.plan`). Options bag `{ forceNew?, name? }`, `metadata.activePlanPath` pointer, dotted hierarchical iterations (`\d+(?:\.\d+)*` → `00`, `00.01`, `00.01.02`), `parent` result for subplans. v2 sessions have no `slug` — the slug is derived from the session title (fallback: id tail).
- `packages/core/src/session/plan-path.ts` (`PlanPath.resolveDir`): shared between `SessionPlan.plan` and the plan agent's edit-permission glob. **Containment hardening kept from v1.18.5:** a configured plan dir must stay inside the location directory or the opencode global data/config roots, else fall back to the default. Simplification vs v1.18.5: no VCS check — the default plan dir is always `<location>/.opencode/plans` (schema `Location.Info` carries no `vcs`).
- `packages/core/src/plugin/plan/plan-mode.txt` is the agent-driven workflow (Managing Plans, dotted subplans, Phase 1–6 incl. mandatory `@plan-review` before `plan_exit`). Overridable via fork `plan.prompt` (with `${planInfo}` placeholder).
- Plan agent permissions: `question`/`plan_create`/`plan_exit`/`plan_complete` allow; `edit` denied except the plan-dir globs (plus `external_directory` allow only when the plan dir resolves outside the worktree). Post-port fix (`6b204ca06c`): push **both** the absolute glob and the location-relative glob — the edit tools assert whichever form they resolve for the target file, and a relative-only match previously missed. Build agent: `plan_complete` allow only (`548b9b236e` dropped the `question` allow — it already comes from the upstream AgentPlugin). Other built-ins (`general`, `explore`, `compaction`, `title`, `summary`) get all three plan tools denied. Config-defined agents keep default access (v1.18.5 applied the deny to every agent via the default ruleset — not portable without touching the agent assembly; acceptable, noted here).
- Fork agent overrides (`agent` section) applied in the same plugin via `ctx.agent.transform`: `system`/`description`/`mode`/`hidden`/`color`/`steps`/`model`/`permissions` (appended), `disabled` removes the agent.

## Plan Tools (`plan_create` + `plan_exit`)

- `packages/core/src/tool/plugin/plan.ts` (`PlanTool` plugin) defines both tools (v2.2.5 tool-plugin idiom: `ctx.tool.transform(editor => editor.add(...))`, permission asserted inside the executor). Registered in `packages/core/src/plugin/internal.ts` `pre` array. Descriptions: `tool/plugin/plan/{create,exit}.txt`.
- `plan_create` (`name?` param) registers a file as the active plan via `session.update({ metadata: { activePlanPath } })`; never writes content. A dotted name = subplan (returns the parent path); plain/omitted = new top-level.
- `plan_exit` confirms the switch via `Form.Service` (Build Agent Yes/No), verifies the plan file exists, writes `session.metadata.planImpl = { status: "implementing", ... }`, `switchAgent(build)`, and admits a synthetic build prompt (default resume — continues execution).
- v1.18.5's `run/tool.ts` CLI display rule for `plan_create` was **not** ported: v2.2.5's `packages/tui/src/mini/tool.ts` falls back to generic formatting for unlisted tools.

## Plan Implementation Plugin (`plan_complete` lifecycle)

- `packages/core/src/plugin/plan-impl.ts` (Effect plugin, registered in `internal.ts` `pre`). State machine `implementing → paused → reviewing → completed` persisted in `session.metadata.planImpl` (so the TUI sidebar and child sessions see it).
- Continuation loop: `ctx.session.hook("experimental.idle", ...)` — input admitted by the hook runs in the same execution instead of the session going idle, so each continuation re-triggers it (this replaces v1.18.5's `session.status`-event listener + 2s debounce + pending set; v2.2.5 publishes no `session.status`). The dead stagnant-counter heuristic from v1.18.5 was dropped.
- `plan_complete` tool (via `ctx.tool.transform`) → `reviewing`, triggers the `@code-reviewer` loop per the REVIEW_PROMPT (sent exactly once per review cycle).
- `/plan_impl pause|resume|stop|status` implemented as a first-class plugin command (`ctx.command.transform`), replacing v1.18.5's config-command template + `command.execute.before` interception.
- Compaction context injection: `ctx.session.hook("compaction", ...)` pushes a plan-status system part.

## Configurable `@`-mention Search Index (ripgrep backend)

- `packages/core/src/filesystem/search.ts`: `SearchConfigOptions` + `configureSearch`/`getSearchConfig` process singleton (ported as-is). The ripgrep layer applies `ConfigFork.loadGlobal()` → `configureSearch` at layer init — before any per-location index builds — replacing v1.18.5's `app-runtime.ts` `searchConfigBoot` (v2.2.5 has no app-runtime; per-location layer init is the boot point). The scan passes `hidden` + the fork ignore list (merged with the home-dir `Protected` excludes).
- Upstream v2.2.5's ripgrep `FindInput` already supports `hidden` and `exclude`; no `ripgrep.ts` changes needed.
- **`search.*` is honored from GLOBAL config only** (layer init reads global fork config; project-local fork config still drives `plan`/`agent` via the per-plugin `loadForLocation`). fff backend unaffected.

## Plugin Host Fix: entrypoint probes match resolver error codes (upstream bug)

- Upstream bug in `packages/plugin/src/host.ts` `resolve()`: each entrypoint probe wraps `resolveModule` in a catch that only swallows errors where `error instanceof Error` **and** `error.code` ∈ {`ENOENT`, `ENOTDIR`, `MODULE_NOT_FOUND`, `ERR_MODULE_NOT_FOUND`, `ERR_PACKAGE_PATH_NOT_EXPORTED`, `ERR_UNSUPPORTED_DIR_IMPORT`}. Bun's resolver throws `ResolveMessage` (proto `ResolveMessage ← Object`, NOT an Error) that carries `code: "ERR_MODULE_NOT_FOUND"` — the `instanceof` gate rethrew every "not found".
- Consequences: an uninstalled npm plugin died on the supervisor's first `install:false` pass (`packages/core/src/plugin/supervisor.ts:162`) instead of returning `{pending}` (`packages/core/src/plugin/module.ts:117`), so the second-pass `npm.add` NEVER ran — v2's npm install cache (`~/.cache/opencode/npm/`, root built in `packages/util/src/npm.ts:139` as `<global.cache>/npm`) stayed empty forever and every npm-declared plugin failed. Missing subpath exports (`./server`, `./tui`) also hard-died the whole plugin reload.
- Fork fix (`45de544d2e` "match resolver error codes across Bun and Node shapes"): match on `error.code` membership regardless of Error-ness — a coded not-found from either Bun or Node is "not found", anything else rethrows. With this, v2 auto-installs npm plugins from the registry on first location boot and tolerates absent subpaths (a package without `./tui` just reports no tui feature).
- History: the first attempt (`a3b4db56b0` "swallow Bun ResolveMessage in entrypoint probes") detected ResolveMessage by `error.name`/constructor name but still inside the `instanceof Error` gate — dead code for Bun's actual shape; superseded but kept in history for the audit trail.

## External Plugin Ecosystem (post-fix reconciliation)

- Local dual-format shims live as **files only** in `~/.config/opencode/plugins/`: `ast-grep.ts` (imports `../ast-grep-bundle/` — bundles live OUTSIDE the plugins dir), `zai.ts`, `preemptive-compaction.js` (+ its `preemptive-compaction.config.json`, ignored by discovery). NEVER create subdirectories there: `packages/core/src/plugin/source-directory.ts:25` turns every subdirectory under `plugin`/`plugins` into a Host-resolved package target (expected to have package.json/exports) instead of a loose file.
- Shims default-export `{id, server, setup}` — v1 calls `server(input)`, v2 calls `setup(ctx)`; v2's `Module` schema (`packages/core/src/plugin/module.ts:75-88`) matches the `{id, setup}` branch and tolerates the extra `server` key, so one file serves both hosts.
- Source repos (own plugins, fixed in place — all on github.com/loquilloll): `opencode-ast-grep`, `opencode-zai-tools`, `opencode-preemptive-compaction`. Reference forks of third-party plugins (with `upstream` remotes): `opencode-ponytail` / `opencode-websearch` / `opencode-notifier` — the upstreams have since shipped v2 support, so the forks are fallback/reference only; the notifier's dual-host 0.2.9 build is what's seeded in both npm caches and what actively loads.
- npm-declared plugins in `~/.config/opencode/opencode.jsonc` now install + load under v2 thanks to the host fix: `opencode-websearch`, `@mohak34/opencode-notifier@latest`, `@dietrichgebert/ponytail`, `@plannotator/opencode@latest` (plan-agent workflow options), and `@prevalentware/opencode-goal-plugin` are all ACTIVE (goal-plugin v0.1.91 contributes the `duplicate-pr` and `triage` agents; an early "bundles effect@3" WARN was debris from a corrupted partial install during the pre-fix era — a clean `npm.add` resolves against the host's effect; suspect stale generations under `~/.cache/opencode/npm/<pkg>@<spec>/` if a package plugin fails oddly, delete to force reinstall). v1 (opf18) keeps its own cache at `~/.cache/opencode/packages/` — unaffected.
- `preemptive-compaction` deliberately no-ops under v2: v2's native auto-compaction covers it (~85% default threshold vs the plugin's 78% — set `compaction.buffer: "22%"` in config to reproduce the plugin's exact behavior). The v1 path is byte-identical.

## Fork Operations / Environment

- DB isolation: the `opf2x` PowerShell profile function pins `OPENCODE_DB=opencode-opf2x.db` (the frozen seed `opencode-pre-opf2x.db` is the rollback snapshot). NEVER point a newer binary at `opencode-opf18.db`; `opencode.db` belongs to npm+dev only. `opf2x` runs `--standalone` (private server per run — no background-service cross-contamination).
- Toolchain: the repo pins `packageManager: bun@1.4.4`; the system bun is 1.3.14 (other worktrees need it). Typecheck via `bun run typecheck:tsc` from package dirs (bun 1.3.14 can't run `bun check`). `.husky/pre-push` gates on the pinned bun version — push with `git push --no-verify` (`typecheck:tsc` is the verified gate). Side-by-side bun 1.4.4 for builds: `~/.local/opt/bun-1.4.4/bun.exe`.
- Source-run cold boot is ~25–40s, so one-shot CLI commands may die with "Location plugins did not finish activating" (noise, not a bug — judge via server logs in psmux). The built exe eliminates this (~0.6s to listening). Build: `& ~\.local\opt\bun-1.4.4\bun.exe run build --single` from `packages\cli` (~6min; embeds web UI, models snapshot, plugin runtime, win32-x64 pty) → `packages\cli\dist\cli-windows-x64\bin\opencode.exe` (~247MB). The `opf2x` profile function prefers the exe and falls back to the source run when `dist/` is absent.
- Verification recipe: in psmux run `serve --port <p> --print-logs`, then `GET /api/agent` + `GET /api/plugin` with Basic auth (`opencode:<printed password>`). opf18 regression check: `session list -n 1` with `OPENCODE_DB=opencode-opf18.db` — expect `[opencode-zai-tools] registered 13/13 tools.` and zero errors. Full fork management is documented in the `~/.config/opencode/skill/opf2x/SKILL.md` skill.
